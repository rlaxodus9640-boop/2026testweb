# 회원가입·로그인 데이터베이스

## 공지사항 게시판

이미지·첨부 지원 SQL `20261014000400_notice_assets.sql`을 원격 적용했습니다. `image_paths`(최대 3장 순서)와 `attachments`(최대 5개 경로·파일명·크기)를 추가하고 비공개 `notice-assets` Storage 버킷을 생성했습니다. 회원은 게시글에 연결된 파일을 읽으며 관리자는 업로드·삭제·편집 중 조회가 가능합니다. 앱에서 1시간 유효한 서명 URL을 생성합니다. 이미지 각 5MB, PDF·TXT·ZIP 각 10MB를 UI에서 검증하며 버킷은 허용 MIME과 파일당 10MB를 제한합니다.

공개 버킷 설정은 자동 승인 검토에서 거부되어 비공개 회원 접근으로 변경했습니다. 브라우저 실제 업로드·다운로드와 Storage 권한 종합 검증은 남아 있습니다. DB 컬럼·버킷 비공개 설정·정책 존재·등록 메타데이터 검증 제약은 확인했습니다.

`migrations/20261014000300_notices.sql`은 공개 읽기·관리자 작성/수정/삭제를 위한 `public.notices`와 RLS·인덱스·수정 시각 트리거를 생성합니다. 2026-10-14 Supabase MCP로 역할 SQL과 함께 적용 완료했습니다. 관리자 계정은 재로그인 후 공지 작성을 이용하세요. 별도 `member_profiles` 테이블은 필요하지 않습니다.

쓰기 정책은 JWT의 캐시된 역할 대신 보안 함수로 DB의 현재 관리자 역할을 확인합니다. 클라이언트에는 제목·본문·중요 표시 수정만 허용하며, 생성자는 새 글 작성 시 본인 UUID여야 합니다. 관리자 CRUD, 생성자 변경 차단, 비로그인 읽기·작성 차단, 일반 회원 쓰기 차단을 DB에서 검사했습니다. 테스트 데이터는 롤백했습니다. 브라우저 CRUD 검증은 남아 있습니다.

SQL 적용 후 관리자 글 생성·수정·삭제, 일반 회원 및 비로그인 쓰기 거부, 타인 생성자 지정 거부, 관리자 역할 해제 후 기존 토큰의 쓰기 거부, 검색·페이지 이동과 빈 결과를 확인해야 합니다. 기존 커뮤니티 예시 글은 공지 테이블에 자동 등록하지 않습니다.

## 계정 역할

`admin`과 `user`는 Auth DB의 `raw_app_meta_data.role`로 관리합니다. 브라우저가 수정할 수 있는 `raw_user_meta_data`와 분리합니다. `migrations/20261014000200_account_roles.sql`은 기존 미지정 계정을 `user`로 설정하고 이메일 인증된 `admin@example.com` 계정을 `admin`으로 지정하며 신규 회원의 기본 역할 트리거를 추가합니다. 다른 앱 메타데이터와 기존 유효한 관리자 역할은 보존합니다.

이 SQL은 별도 프로필 테이블 마이그레이션 없이 적용할 수 있습니다. 지정 계정이 없거나 이메일 인증 전이면 트랜잭션이 실패합니다. 이메일 변경이나 탈퇴 후 같은 이메일 재가입만으로 관리자 권한을 자동 부여하지 않습니다. 2026-10-14 원격 적용 후 지정 이메일의 `admin` 역할과 신규 계정 기본 `user` 역할을 확인했습니다.

적용 후 해당 사용자는 재로그인하고 마이페이지에서 역할을 확인하세요. 관리자 데이터 API를 추가할 때는 서버나 RLS에서 역할을 검사해야 합니다. 브라우저 UI에서 역할을 읽는 것만으로 서버의 접근 권한이 바뀌지는 않습니다.

## 마이페이지 저장 (현재 구현)

이름과 캐릭터 설정의 현재 원본은 Supabase Auth DB `auth.users.raw_user_meta_data`입니다. `/mypage`에서 `auth.updateUser({ data: { full_name, avatar_config } })`를 호출해 한 번에 저장합니다. `avatar_config`에는 `character`, `color`, `background`, `expression`, `accessory`를 저장합니다. SVG는 이 설정으로 브라우저에서 다시 생성합니다.

프로필 변경은 Auth DB에 저장되며 별도의 `public.member_profiles` 테이블 생성 없이 동작합니다. 아래 마이그레이션의 프로필 테이블은 현재 UI에서 사용하지 않습니다. 추후 해당 테이블을 사용할 경우 Auth 메타데이터와의 동기화 방식을 먼저 확정해야 합니다. 사용자 메타데이터는 표시용이며 접근 권한 판단에 사용하지 않습니다.

로그인 후 마이페이지에서 이름·캐릭터를 변경하고 저장한 뒤, 새로고침·재로그인 시 복원되는지 확인하세요. Supabase 대시보드 Authentication 사용자 상세의 메타데이터로 저장값을 확인할 수 있습니다. 실제 계정으로 이 시나리오를 검증한 상태는 아닙니다.

## 적용 방법

1. 대상 프로젝트의 기존 테이블·함수·트리거와 이름 충돌이 없는지 확인합니다.
2. Supabase SQL Editor에서 `migrations/20261014000100_create_member_profiles.sql`을 한 번 실행하거나, 연결된 Supabase CLI의 마이그레이션 절차로 적용합니다.
3. 테이블, RLS, 정책, 권한과 트리거를 확인합니다. 동일 SQL을 중복 실행하지 않습니다.
4. 테스트 계정 가입 후 프로필 생성, 본인 조회·이름 수정, 다른 회원 및 비로그인 접근 차단을 확인합니다. 계정 삭제 시 프로필도 삭제되는지 확인합니다.

마이그레이션은 트랜잭션으로 구성했습니다. 기존 계정은 프로필을 생성하며 과거 안내 확인 시각은 추정하지 않습니다. 기존 Auth 테이블 구조는 변경하지 않습니다.

## 화면 연동

`AuthPage.jsx`에서 아래 형태로 실제 API를 호출합니다. 인증 상태와 로그아웃은 `AuthStatus.jsx`, 클라이언트는 `supabase.js`에서 관리합니다. 프로필 생성은 위 SQL 적용 후 동작합니다.

```js
await supabase.auth.signUp({
  email,
  password,
  options: {
    data: { full_name: name.trim(), demo_notice_acknowledged: true },
  },
})
await supabase.auth.signInWithPassword({ email, password })
```

안내 확인 정보는 데모 확인 기록이며 실제 약관 동의 증빙이나 권한 판정에 사용하지 않습니다. 사용자 메타데이터는 사용자가 변경할 수 있으므로 권한 부여에 사용하지 않습니다. 실제 운영 전 약관·개인정보 처리방침과 동의 기록 설계를 확정해야 합니다.

프로필 생성 트리거가 실패하면 가입도 실패할 수 있으므로 실제 가입 테스트가 필요합니다. 브라우저는 본인 프로필 조회와 이름 수정만 허용하며 프로필 생성·삭제·확인 시각 수정은 허용하지 않습니다.

Supabase Authentication의 URL Configuration에서 현재 개발 주소와 운영 주소의 `/login`을 Redirect URLs에 등록하세요. 이메일 인증 후 해당 주소로 돌아오며 SDK가 세션을 처리합니다. 이메일 인증을 켠 상태와 끈 상태는 가입 응답이 다르므로 모두 확인해야 합니다.

API 연결 코드는 빌드·린트로 확인하되 실제 계정을 사용한 가입·메일 확인·로그인·세션 복원·로그아웃은 별도 검증해야 합니다. 역할·공지 SQL 원격 적용 및 DB 접근 검사는 완료했으며 별도 프로필 테이블 SQL은 적용하지 않았습니다.
